# 模块状态与 QQ 通知设置

## 范围

PixelMiPushFramework 的首页显示模块工作状态，设置入口为「设置 → 模块设置」。QQ 通知角标、会话头像布局和汇总通知简化是三个独立开关，首次使用均开启。基础设备伪装和跨应用通知发布保持原样。

选项保存在 Pixel MiPush 的私有配置中。推送服务只显示模块确认保存的结果，不另存一份。保存失败时保留原选择并提示重试。

配置通过内容观察者同步到推送服务和 SystemUI。修改用于后续通知呈现，已有通知需重新发布。布局关闭时，会话图标视图在后续绑定中恢复修改前的尺寸和边距。尚未取得有效配置时，暂停额外 QQ 定制，并报告配置未就绪。

## 状态依据

- 推送服务增强：当前推送服务进程中的通知桥接安装完成，并已注册存活的 Binder 端点。
- 系统通知增强：从该进程实时查询既有系统通知增强标记，与通知操作使用同一判断入口。
- QQ 样式增强：SystemUI 中角标和头像布局两个具体 Hook 均安装完成，且端点能响应。
- 配置同步：端点报告的配置修订号与模块保存的修订号一致。配置尚未同步时单独提示，不显示为完整就绪。

这些状态表示对应能力已加载或就绪，不证明 QQ 新注册、服务器消息接收、客户端设备伪装或每条通知均成功。关闭定制选项也不等于卸载对应 Hook。

模块进程重建后，注册表从空状态开始。框架恢复前台或用户重新检查时，发出只读发现请求，已注入的宿主重新注册。进程退出后的端点无法响应，不沿用磁盘上的历史就绪记录。

## 接口与权限

唯一协议定义位于 `module-api/src/main/java/com/neko7ina/pixelmipush/api/ModuleContract.java`。它是纯 Java 库，由模块和配套框架共同编译，不复制常量、Bundle 字段或 Binder 协议。

模块的 ContentProvider 实现持久化、状态查询和运行端点注册。读写按 Binder 调用 UID 对应的安装包校验：

- 推送服务可读写配置，并只能注册自己的端点。
- SystemUI 可读配置，并只能注册自己的端点。
- 模块自身可读状态。
- 其他 UID 无权调用控制接口。共享 UID 按 Android 的同一安全主体处理，不声称能区分共享 UID 内的应用。

运行端点只接受模块 UID 的探测。发现广播仅要求宿主重新注册，不接受配置输入。协议版本不匹配时，框架要求更新模块，而不猜测字段含义。

## 构建与验收

模块构建自动包含 `:module-api`。框架默认从相邻的 PixelMiPush 克隆读取该项目，亦可通过 `-PpixelMiPushDir=<路径>` 指定。框架 CI 按自身的 `module-api.ref` 检出固定模块提交，因此须先推送对应模块提交，再推送框架提交。

本轮模块 Release 构建通过。包名、长期签名、targetSdk、已有推送协议和发布版本号未变；本机没有恢复签名材料，构建包不作为正式装机附件。后续常量归并与布局状态同步修改通过定向编译后记录在 STATUS。

框架保留一条真实页面流程测试 `ModuleSettingsTest`：进入模块设置，逐一切换选项，核对其他选项保留及两宿主配置确认，结束后恢复原设置。它需要另行授权的测试环境和已启用的两个候选，不在当前主设备上自动执行。

尚需真实设备确认首页状态、次级页面进退、三项定制独立开关及重启后的配置恢复。静态编译和本地 APK 不替代模块作用域、真实通知或发布附件装机验收。
