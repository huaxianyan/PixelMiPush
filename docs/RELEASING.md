# 发布约定

## 包名迁移

后续版本使用 `com.neko7ina.pixelmipush`，沿用模块长期签名。历史 Pixel 包为 `com.neko7ina.mipush.pixel`，新包独立安装，不能覆盖旧包。

首次新包发布的说明必须提醒用户关闭旧 LSPosed 模块，安装并启用新模块，重新设置作用域和模块私有配置，然后手动重启。旧包删除与设备安装不属于工作流操作。

API 102、通知行为和框架包名保持不变。历史版本的设备验收不等于新包名已通过设备验收。

## 版本与说明

模块从 `v1.0.0` 开始使用独立版本线，不再沿用历史日期版本。标签为 `v<版本>`，APK versionName 与去掉 `v` 的标签一致。

versionCode 默认值在根 `build.gradle` 显式维护，每次正式发布递增，不随 Git 提交历史计算。构建参数可覆盖该值，正式版必须高于已分发测试包的 versionCode。正式发布由标签触发，手动 workflow_dispatch 只构建验证产物。

每个新标签必须包含 `docs/release-notes/<标签>.md`。说明不以一级标题开头，按实际内容分「新功能」和「问题修复」，每条以加粗小标题开头，不把内部重构硬归为修复。

说明链接同一标签下真实存在的详细文档，不手写构建信息。工作流从实际 APK 追加构建信息后，最终正文最多 40 行。

模板：

```markdown
这版新增……，修复……。

## 新功能

- **功能名**：说明用户获得的能力

## 问题修复

- **问题名**：说明受影响场景和修复结果

完整记录见 [详细说明](https://github.com/huaxianyan/PixelMiPush/blob/v<版本>/PIXEL-API102.md)。
```

只有一种改动时删去另一节。包名迁移是升级注意事项，不为了凑分类写成问题修复。

## 产物

- `PixelMiPush-<版本>.apk`
- 同名 `.apk.sha256`，使用 `sha256sum -c` 可读的 LF 文本格式

当前没有原生库，也没有限定架构，文件名因此不带架构段；构建信息里的架构一格写 `无原生库`。构建信息包含版本、versionCode、包名、架构、min／target SDK、签名证书、源码提交和 APK SHA-256。

发布门禁保留 API 102 元数据、Legacy API 检查和包名检查，标签构建必须使用现有长期密钥。`prepare_release.py` 验证实际 APK 的长期证书与 v2 签名、标签与检出提交、versionName 和详细文档，再命名附件。

## 流程

1. 准备版本化说明，运行 `python scripts/verify_release_notes.py --tag v<版本>`
2. 合入已验收代码并确认普通 CI 通过
3. 创建并推送注解标签，触发 `ci.yml` 的正式发布步骤
4. 核对线上附件名称、包名、签名和哈希，安装与重启另行授权

标题只使用标签，不自动生成说明，不覆盖已有 Release 附件。历史版本和附件保持原样。

README 的 Obtainium 入口只选择新命名的正式版 APK。旧包用户需手动完成第一次迁移。
